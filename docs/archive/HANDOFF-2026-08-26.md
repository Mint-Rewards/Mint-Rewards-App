### Correctness — reachable defects and unmeasured claims

**5. Phase prefill accuracy was never measured.** The P0.6 gate that cleared DHA and Korangi
(n>=20, >=85%) measured **area-level** agreement. Sub-area accuracy has no evidence behind
it. A pin near a phase boundary can pre-select the wrong phase; the field is mandatory, so a
user who does not notice saves a wrong address. Gating or removing it is `subAreaFromHint`
plus one branch. Same evidence bar that keeps 218 areas at `geocodePrefill: false`.

**7. The two registry resolvers have genuinely diverged.** The app resolves "<Town>
<SubArea>" strings; the backend cannot, because sub-area lists are not in
`lib/data/locationRegistry.json`. The app compensates client-side. The durable fix is
exporting sub-areas into the shared artifact so the backend resolves AND caches them —
`scripts/export_location_registry.ts` plus both committed copies.

**10. The geocode cache appears never to persist.** After a successful live lookup the
`geocodeCache` collection did not exist in `mint_rewards` at all, though the write is
unconditional once LocationIQ returns a usable address. Only `.env` defines `MONGODB_URI`
and it is the same database, so it is not a wrong-DB artifact. If it never persists, every
lookup burns a LocationIQ call and the 3s timeout. Not chased — it blocks nothing.

**11. OSM attribution is owed and is not surfaced.** The centroids are ODbL, which requires
attribution and share-alike. Nothing in the app credits OpenStreetMap. A licence obligation,
not polish; the map picker is the likeliest home.

**12. `LOCATIONIQ_API_KEY` in the DEPLOYED backend is unverified.** Set locally now, which is
why the prefill works on a laptop. Production is unknown; unset, every confirm modal falls
back to the user's own saved values and the prefill never happens.

**13. `activatedCitiesOnly` reads coverage tier "A" as the proxy for "activated"** — today
Karachi only. Nothing in the client carries a real activation list. Isolated in
`isActivatedCity()`. Do not enable that flag in production until it is agreed.

**14. `evaluateLocation.ts`'s header is now false.** It says "the client contains no
completion logic of its own". That stopped being true when the gate shipped, and the client
now has three separate definitions of complete.

### Deliberately inert — correct as-is, listed so nobody "fixes" them

**6. A province change in the confirm modal destroys a correct pin — RULED INTENDED
(owner, 2026-08-26).** Province clears the city and a city change clears the pin, so using
the filter to fix a wrong city throws away a pin that was right. Kept, because it is not the
same shape as the town inversion it resembles. A town is PRODUCED by the pin, so clearing
the pin on a town edit destroys the evidence being corrected — that was a real loop. A
province is not produced by anything: it is chosen, upstream of the city, to narrow a list of
58, and changing it says the whole place is wrong rather than that one derived label was read
wrongly. Carrying a coordinate across it would let a Karachi pin sit under a Peshawar address
and pass validation — the exact pairing the screenshot showed, and the one the mandatory
cascade exists to prevent. The cost is a re-pin for someone using the filter as a search box;
one map tap, against a silently wrong address. `CLEARED_BY_PROVINCE_CHANGE`'s doc comment
carries this reasoning and says not to "fix" it.

**18. `pinReducer`'s `centroid` event is still never dispatched.** A centroid is where an
area is, not where a person lives, and a marker nobody placed can be confirmed by accident.
The dataset landing does not change this: centroids position the CAMERA only.

## Issue 8 · a legacy user is no longer marched through a re-pick

Province became mandatory on 2026-08-26. `province` is a form-only filter — it is derived
from the city at payload time, never asked for — so for a city the registry does not know it
derived nothing, the field sat empty, and the save was blocked. The only escape was to pick
a province, which fires `CLEARED_BY_PROVINCE_CHANGE` and takes the city, town, house number
and pin with it. A user who opened Edit Profile to add a house number was made to re-enter
their whole address.

There is a value available that nobody was reading: `user.province` **is** persisted. It has
to be — `isProfileComplete` requires it, which is the whole reason these users are being
gated in the first place. They answered it years ago, when the dropdown still existed.

Two changes, and the ORDER is the decision in both:

1. `useLocationForm`'s `reset` now resolves province as
   **registry(city) ?? carried-in value ?? ""**, and both hosts (`editProfile` and
   `ConfirmAddressModal`) now pass `user.province`. Registry first is what stops a stale
   stored province from contradicting a city the registry knows — the pairing the derived
   field exists to make impossible.
2. `resolveProvinceForPayload(city, fallback)` applies the same order on the way out.

**The second change is the one that actually mattered**, and it was not in the original issue
text. Fixing only the form would have let the user save — and `buildLocationPayload` would
have sent `province: ""` for their off-registry city, overwriting a stored province with
nothing. They would have come out of the edit *less* complete than they went in, and the gate
would have re-armed on the next launch: a loop, reached by doing exactly what the app asked.

"" is still the answer when neither source knows — the pre-existing P0.2d null path, and
still correct, because at that point nobody has ever answered the question.

6 new tests (`useLocationFormFlow`, `locationForm`) covering all three branches in both
places, including the disagreement case.

## Issue 9 · built — the app asks instead of guessing

**The problem.** A town edit no longer clears the pin (owner ruling, 2026-08-26), and that
ruling is right: under Province -> City -> Pin -> town the pin PRODUCES the town, so clearing
it on a town edit destroyed the evidence being corrected and left the user unable to save.
The residual is that a user who genuinely moved house within one city can change their town
and keep a pin describing their old address. For a collection service the pin is the routing
field, so that is a truck at the wrong door.

The two edits are identical in form state and obvious to the person making them:

- (a) "the geocoder read my coordinate wrongly" -> the pin is right. Common. What the ruling
  protects.
- (b) "I moved" -> the pin is wrong. Rare, and today silent.

**What shipped.** A sheet with three answers — *I've moved house* (clears the pin and opens
the map), *The area name is wrong* (today's behaviour, unchanged), and *Cancel* (backs out of
the edit entirely). Android back maps to Cancel, because the only safe default is the one
that changes nothing.

### The gate is the interesting half

`townChangeNeedsConfirm()` fires only when **all** of these hold: there is a town to lose,
there is a pin, `placementRef.current === null` (the pin was rehydrated, not placed this
session), and `derivedRef.current.town === false` (no prefill wrote this town from the pin
now on the map). Any one of the last two failing means the pin and the town are a fresh,
consistent pair, so the edit can only be case (a) — and the prompt stays out of the way.

That is what keeps the town ruling intact rather than quietly undoing it. **The common path
is never interrupted.**

### The bug this turned up

`reset` unconditionally set `derivedRef` to `{ town: false, subArea: false }`, with a comment
saying "a rehydrate is not a prefill". True for Edit Profile. **False for the confirm modal**,
which resets with a town the geocoder produced from the pin seconds earlier. Left as it was,
the prompt would have fired on every correction of a geocoder mistake in the one screen built
to collect them — precisely the loop the town ruling removed.

`reset` now takes a third argument, `derived`, and `ConfirmAddressModal` passes
`{ town: townIsGeocoded }` — reusing the exact condition it already computed for
`suggestedAreaRef`, so the two cannot drift. This also un-breaks something that was already
wrong and unnoticed: `applyPinPrefill`'s "clear a stale derived town when the new pin
resolves to nothing" branch could never fire in that modal, because the flag it reads was
always false.

### Where the answer goes

`trackTownChangeResolved("moved" | "relabelled" | "cancelled")` — a new `town_change_resolved`
event. This is the point of asking rather than guessing, and it decides the prompt's own
future: if `moved` is vanishingly rare the interruption is not paying for itself and should
be narrowed or dropped; if it is common, stale pins have been reaching routing data all
along. Watch `cancelled` — a lot of it means the sheet reads as a warning rather than a
choice.

### Why not the alternatives

- **Revert the town ruling.** Reintroduces an unsaveable loop that blocked *everyone*, to
  protect against a case affecting only movers. Strictly worse.
- **A distance rule** (clear the pin when the new town's centroid is far from it, by analogy
  with `isFixWithinCity`). Town centroids cover 214 of 263 areas, so for roughly a fifth of
  towns it silently does nothing. Partial coverage on a safety check is the worst outcome:
  the complexity ships, the protection does not, and nobody can tell which case they are in.
- **Always clear on a rehydrated pin.** Cheaper, but it punishes case (a) — the common one —
  with a forced re-pin, which is most of the pain the ruling removed.

### Tests, and what is NOT covered

15 new tests. 9 in `useLocationFormFlow` for the decision (held pending; each of the three
answers; all three entry points — picker, "Other", back-to-list; and four separate reasons it
stays silent, including the confirm-modal case and a pin placed this session). 6 in
`townChangeModal` for the wiring, including Android back.

### Attempting QA 59 found the defect before the device did

QA 59 exists because "I moved" opens the map through a third route — `onOpenMap`, an
**optional** prop threaded from the host through `LocationFields`. Optional is the dangerous
part: omit it and nothing fails to compile and nothing throws.

`ConfirmAddressModal` was not passing it.

The reasoning that made that look safe was mine and it was wrong. I had it that the confirm
modal never shows the prompt, because `reset` is told the town is geocoder-derived. True —
**while the geocoder succeeds.** When the lookup fails, or returns a town that is not
canonical for the user's city, `buildPrefill` falls back to their SAVED town, `townIsGeocoded`
is false, nothing derived it, the pin is rehydrated — and the edit is ambiguous again, in a
modal with no map to open. QA 56 already covers running with `LOCATIONIQ_API_KEY` unset,
which is today's production state, so this was not a corner case: **it was the default
path in production.**

Fixed — the modal now passes `onOpenMap={() => setMapVisible(true)}`, the same handler its
"Adjust pin" chip uses.

**5 more tests** (`townChangeOpensMap`), which render `LocationFields` against a REAL
`useLocationForm` — the first test in the repo to render that component, since it reaches
`config/env.ts` and needs the same stub `confirmModalAdjustPin` uses. Four cover the seam
(map opens on "moved" and only on "moved"; a host with no `onOpenMap` degrades instead of
throwing). The fifth is a source check asserting **both** hosts pass the prop — verified
against `HEAD`'s copy of the modal, where it fails, so it demonstrably catches this defect
rather than merely describing it.

**QA 59 has since passed on a simulator** (2026-08-26): the sheet appeared on Edit Profile,
and "I've moved house" cleared the pin and opened the map. The light comes on.

What that pass does NOT cover is the path this defect was actually on — the confirm modal
with the geocoder unavailable, which is QA 59b and is still owed.

## This pass — the last two open items, both closed

### P2-15 · a house number now dies with its city, not its town

`hooks/useLocationForm.ts`, plus `__tests__/locationFormClearing.test.ts`.

Option 2 of the three, as recommended: **a CITY change clears `houseNo`; a TOWN change keeps
it.** A coordinate is absolute and is provably wrong after any place change. A house number
is relative — "14-B" is meaningless without its area rather than incorrect within it — and
someone who mis-taps a town and corrects it usually still lives at 14-B, so clearing there
would force a pointless retype. A different city is the stronger signal, and since the field
is mandatory a value carried across one satisfies validation and saves silently against an
address it was never written for.

The clearing sets are now two exported constants, `CLEARED_BY_CITY_CHANGE` and
`CLEARED_BY_TOWN_CHANGE`, spread by all five paths that change a place (city picker, town
picker, "Other", a did-you-mean suggestion, back-to-list). The asymmetry is therefore
**stated once and asserted directly**, rather than being an emergent property of five copied
object literals — which is how this repo previously lost a block that survived its town.

This has a QA consequence that REVERSES an earlier instruction: old step 35 said a house
number surviving a city change was correct. It is now a bug. See step 35 below.

### P2-6 · the centroid dataset, sourced

`utils/pakistan_areas.ts` (the two tables), `scripts/geocode-spike/centroid-sweep.js` (new,
the generator), `utils/locationForm.ts`, `utils/locationAnalytics.ts`,
`components/ui/MapPicker.tsx`, `utils/__generated__/locationRegistry.json` (regenerated),
plus `__tests__/centroidDataset.test.ts`.

**54/58 cities and 214/263 areas.** Nothing was invented.

The generator forward-geocodes every registry name through **two independent gazetteers**
and keeps an entry only where they agree:

- The shipped coordinate is always **LocationIQ's** — hosted Nominatim, so OSM-derived and
  ODbL, which permits a persistent lookup with attribution.
- **Google** geocodes the same name as an independent **check only**. Its coordinates are
  not in the file and were never averaged in: its terms forbid building a persistent lookup
  from its output, so it gates acceptance and contributes no value.

Tolerances are sized against **the viewport the number feeds**, not against any idea of
correctness — 20km for a city (`CITY_DELTA` 0.2° ≈ a 22km view), 5km for an area
(`AREA_DELTA` 0.05° ≈ 5.5km). A disagreement smaller than the viewport cannot push the right
rooftops off screen. Among accepted entries the providers' median gap is 0.54km.

**Partial coverage is the design, not a shortfall.** A miss costs nothing — an area falls
back to its city, a city to `PAKISTAN_CENTER`, which is exactly today's behaviour. A wrong
centroid opens the map on a confident, plausible, wrong neighbourhood, which is why these
tables stayed empty for a release rather than being hand-filled. **Every one of the 48
rejected areas still gets a city-level view**; only Ghanche, Ghizer, Hub and Kotli fall all
the way back to the country, and none of them has town data anyway.
`scripts/geocode-spike/out/centroids-report.md` names every rejection and its reason.

Two guards earned their place on the first run and are worth knowing about, because both
describe how this kind of dataset goes wrong quietly:

1. **Query phrasing, not coverage, nearly cost a whole city.** LocationIQ returned one
   identical point — "Sector G, DHA Phase 2", ~25km off — for *every* `Sector X-Y,
   Islamabad` query. Google answered all of them correctly. Islamabad would have been
   dropped over the word "Sector". Asking for "F-6" as well as "Sector F-6" recovered them.
2. **A duplicate-point check, run over the whole sweep at the end**, revokes any coordinate
   that two names claim. It caught 7 entries that cross-provider agreement had *passed*.
   Both claimants are revoked, never just the second — nothing says which name the point
   belongs to.

`__tests__/centroidDataset.test.ts` re-asserts those same rules against what actually
shipped: every key resolves to a real registry entry, every point is inside Pakistan (which
is also the lat/lng-swap detector), no point is claimed twice, and no area sits more than
60km from its own city. The sweep runs by hand and roughly never, so a bad paste or a
hand-added "obvious" entry would otherwise reach users with nothing in between.

**`viewportSource` gained two values, and this was not optional.** `map_opened` now reports
`area_centroid` and `city_centroid` alongside `saved_pin` / `device_gps` / `default`.
Without them the dataset would have silently redefined `default` from "the user was shown
the whole country" to "the whole country OR their own city" — retiring the one population
worth counting, with no dashboard change to explain the drop. Their ratio is also the live
read on how often area coverage actually helps.

**Regenerating:** both keys in `.env.geocode`, then
`node scripts/geocode-spike/centroid-sweep.js` (~10 min, resumable, every response cached in
`out/centroid-cache.json`). Paste `out/centroids.generated.ts` over the two tables.

## Running it on a device — the first simulator session

Everything in this section came out of the first time the gate work ran outside a test. Most
of it is committed in `1796067`; the tail (the evaluation message, the placement fixes, the
province rung, mandatory province) is still in the working tree.

### Why the modal never appeared, and why it was not a bug

The gate was silent for every user. It turned out to be **the fail-open rule working
exactly as designed**: `mint-rewards-backend-dev.vercel.app` serves `/api/app-config`
without a `locationGate` key at all, because the route change that adds it lives only on the
backend's unmerged `feature/location-capture-p0`. No `locationGate` -> `normalizeLocationGate`
returns null -> `resolveLocationGate` resolves "config unavailable" -> no modal, for
everybody.

Nothing was changed in the client for this. Patching it would have meant weakening the one
property that stops a broken config locking the userbase out. **The dev deployment still
does not serve the config** — the app is currently pointed at a local backend instead.

Two things follow that outlive this session:

- **QA step 42 is currently unfalsifiable.** "Point at an unreachable backend, get no modal"
  is indistinguishable from the normal state until the config is actually served somewhere.
- `.env` is read by `app.config.js` at **dev-server start**. Editing it and reloading does
  nothing; `npx expo start -c` is required. This cost a full debugging round.

### A one-second delay before the modal appears

`GATE_APPEARANCE_DELAY_MS` in `components/LocationGate.tsx`. Home paints first, so the modal
reads as a prompt about a screen the user has arrived at rather than as part of the
navigation. It re-arms per visit, and the reset lives in the effect's **cleanup** rather than
its body — a synchronous `setState` there cascades a second render on every navigation away
from Home, which the `react-hooks` lint catches.

It is a display delay only. It does not touch the decision, so someone who bounces off Home
inside a second is not thereby exempt.

### Two defects, and they had to be fixed together

Neither was visible from a test suite of pure functions. Fixing either alone makes things
worse than leaving both.

**1. The gate could never come back.** `dismissedOnPath` was set on dismiss or on
"Continue" and never cleared. Its comment claimed returning to Home re-arms the gate, but
comparing a stored path against the current one cannot detect a round trip — you come back
to `/home` and it still equals `"/home"`. So the modal went silent for the rest of the app
run whether or not anything was filled in. It now clears on leaving Home.

It deliberately does **not** clear `dismissals`. That count is the soft-mode nag budget, and
refunding it on every navigation would make a soft gate infinitely repeatable.

**2. A completed profile would not have silenced it.** This one only bites once #1 is fixed,
and it produces an inescapable modal. `resolveLocationGate` reads `user.locationVersion`;
the PATCH stamps it server-side, but `updateProfile` calls `getProfile()` *before* the PATCH
runs, so the refetched user carries the pre-bump value. `setLocationEvaluation` stored the
verdict in its own field and never touched the user — so its comment ("storing the
evaluation is what lets the gate fall silent without a refetch") was simply false. It now
writes the version onto the user.

> **The field is `evaluation.currentVersion`, never `evaluation.version`.** `version` names
> which questionnaire is current and comes back to EVERY caller including incomplete ones;
> writing it would mark the entire userbase complete and disable the gate permanently. There
> is a test pinning exactly that.

### The checklist rows are buttons now

Tapping an outstanding row opens Edit Profile **on that field**. The chevron had always
rendered on exactly the outstanding rows, so the affordance was already promising a tap that
nothing listened for.

`utils/profileFocus.ts` holds the four destinations and parses the route param — parsed, not
cast, because it crosses a navigation as untrusted input and a stale deep link from a release
that renamed a field must degrade to "open the form normally".

The rows are not the form's fields, and the mapping says so: **Name** and **Phone** scroll
*and* focus their input; **Pickup address** scrolls to the block, because city/town/sub-area/
house-number are one question to a person and four inputs on screen; **Map pin** scrolls to
the pin button; **Email** is never tappable, being read-only and set at signup.

A row tap suppresses the modal **without spending a dismissal**, same as Continue —
engaging with the gate is the opposite of skipping it, and otherwise three taps on the
checklist would harden a soft gate against a cooperating user.

Judgement call worth revisiting: **"Map pin" scrolls to the pin button rather than opening
the map.** One extra tap, but consistent with this repo's standing refusal to put a user in
front of a map they did not ask for — the same reasoning that keeps `pinReducer`'s
`centroid` event unused.

### The capture order is now Province -> City -> Pin -> the rest

Owner request, same simulator pass. `LocationFields` renders in that order and the pin
supplies what follows it.

**Why the pin sits third and not first.** It needs a city above it in two directions at
once: `getSelectionRegion` aims the map at the city centroid — which is what the P2-6
dataset was for, and which a pin-first form would have made inert overnight — and
`buildPrefill` scopes its name resolution to a city. Pin-first would open every user on
PAKISTAN_CENTER and resolve nothing. Third is the position where both work.

After a pin is confirmed, `prefillFromPin` reverse-geocodes it and fills **town, sub-area
and street**. Three deliberate exclusions:

- **City is never overwritten.** The user picked it before dropping the pin, so it is an
  answer, not a guess. A geocoder that disagrees is describing where the pin landed, which
  can legitimately be across a boundary from where someone lives.
- **House number, never.** The geocoder cannot know it. It is the field the user always
  types, which is why it is mandatory.
- **Blanks only.** The request has an 8s budget and the user keeps typing while it is in
  flight; a late reply must not replace a town they picked in the meantime. Filling only
  unanswered fields makes the outcome identical whether the geocoder answers in 200ms, in
  8s, or never — and never is the current production state (open item 5).

The province picker is `showProvince`, default true, and the **confirm modal passes false**.
That sheet exists to ask for as little as possible and arrives with the city already
resolved from the pin, so a find-your-city filter has nothing to do there.

`CLEARED_BY_PROVINCE_CHANGE` joins the other two clearing sets, and a test asserts they
nest — town ⊂ city ⊂ province. Changing province clears the city, which looks aggressive
for a mere filter; the alternative is a city that stays selected while being absent from the
list, which the user can neither see nor re-pick.

### GPS could hijack the camera off the selected city

Reported from the simulator as "the map isn't centering on the city selected", and it was
not the centroid lookup. `requestAndCenter` ran on every open without a saved pin and
`animateToRegion`'d to the device fix, overriding the centroid `initialRegion` had just set.
An iOS Simulator reports Apple HQ unless told otherwise, so the camera flew from Karachi to
California every time.

**The unconditional centering was correct when it was written.** With no centroids the
alternative was PAKISTAN_CENTER, which a fix anywhere on earth improves on. Centroids gave
it a real competitor, and nothing revisited the comparison.

`isFixWithinCity` (60km, the same figure the sweep uses for area containment) now gates it:
a fix near the selected city still wins — it is the best possible viewport for someone
standing at the address they are entering — and a distant one is ignored for centering, so
the map stays on the city. With no city, or a city the sweep never confirmed, it returns
true and the old behaviour is kept exactly where the new data cannot improve on it.

A rejected fix reports `viewportSource` as the centroid, not `device_gps`, and leaves
`gpsCentered` false so the footer does not claim to have centered on the user.

This also affects real users, not just simulators: entering a relative's address, or
travelling, produces the same wrong-city fix.

### Making the pin prefill actually fire (four faults, in order)

The prefill shipped inert. Each fix uncovered the next; none was visible without a device
and a live geocoder.

1. **No key on the local backend.** `LOCATIONIQ_API_KEY` was set in the app repo's
   `.env.geocode` (where the centroid sweep reads it) but the reverse-geocode route is
   server-side. Unset, it short-circuits to `{resolved:false}` without a network call. Added
   to the backend's gitignored `.env`.
2. **Urdu.** LocationIQ answered `"کراچی ڈویژن"`, `"ضلع کراچی"`. Node's undici sends
   `Accept-Language: *` when nothing is set and LocationIQ reads `*` as "return the NATIVE
   name", so nothing could ever match a Latin-script registry. **This was already known and
   written down** — `scripts/geocode-spike/fetchWithPolicy.js` pins the header and explains
   why — and the lesson never reached the backend route. Now pinned there in both the header
   and the query string, with a test.
3. **`"Karachi Division"`.** LocationIQ names the city rung with the division, which is not
   a registry city — so, exactly as `deriveGeocodeFields`'s own IMPORTANT-2 comment
   predicted, every candidate was scoped to nothing and `"Defence"` (a curated DHA alias
   that resolves perfectly under `"Karachi"`) resolved to null. **Every area in Karachi
   failed this way.** `normalizeGeocodedCity` strips `Division`/`District`/`Tehsil` but only
   adopts the result when it IS a registry city, so a genuinely unknown city still comes
   through untouched and still logs. No registry city ends in one of those words — asserted,
   not assumed.
4. **`"DHA Phase 8"` is a town plus a sub-area.** Both resolvers only ever matched towns and
   aliases, never sub-areas, and OSM labels most of DHA by phase. The BACKEND cannot fix
   this: its registry copy carries no sub-area lists, so the string is unresolvable there by
   construction and arrives in `unmatched`. Fixed at the rung where the data is complete —
   `resolveGeocodedName` gained a final town-plus-sub-area pass, and `buildPrefill` now runs
   a second pass over `unmatched` scoped to the user's own city.

That last one also made the app's `resolveGeocodedName` non-dead: it had **no production
caller at all** before this, existing only as the mirror of the backend's.

**The phase is prefilled too.** The same string names both rungs, so discarding the second
half asked the user to re-enter a required field the geocoder had already answered.
`extractSubAreaForTown` returns the REGISTRY's spelling of whatever the remainder
fold-matches, so nothing raw reaches a canonical field; `blockHint` covers the case where
the server resolved the town and the phase survives only in the hint. A remainder that is
not a real sub-area drops the whole candidate — "DHA Phase 99" and "DHA Marina" both resolve
to nothing rather than folding down to "DHA" on a shared prefix.

> **CAVEAT, and it needs an owner call.** The P0.6 gate that cleared DHA and Korangi for
> prefill (n>=20, >=85%) measured **area-level** agreement. Phase-level accuracy was never
> measured. A pin near a phase boundary can pre-select the wrong phase, and the field is
> mandatory, so a user who does not notice saves a wrong address. It is a pre-selection they
> can change, and the alternative is a blank required field — but if the standard here is
> the same one that kept 218 areas at `geocodePrefill: false`, the phase should be measured
> before it ships. Easy to gate or drop: it is `subAreaFromHint` plus one branch.

### A new pin now REPLACES the town and sub-area (owner request)

The first cut filled blanks only. That protected against the race — an 8s reply landing
after the user had typed — but it also meant a corrected pin could never correct the town
its predecessor had set, which is the opposite of what a deliberate re-place means.

Both hold now because staleness is decided by **which pin the answer is about**, not by
whether the field is empty. `confirmPin` returns a token, the caller hands it back to
`applyPinPrefill`, and a reply carrying an old token is dropped — so overwriting is safe.
`clearPin` and `reset` bump it too.

The second half is `derivedRef`, which records whether the town / sub-area were WRITTEN BY a
prefill or chosen by the user. It decides the hard case — a new pin that resolves to nothing:

| in the field | new pin resolves | outcome |
|---|---|---|
| derived from the old pin | to a town | replaced |
| derived from the old pin | to nothing | **cleared** — it described a coordinate that is gone |
| chosen by the user | to a town | replaced (moving the pin is a deliberate statement) |
| chosen by the user | to nothing | **kept** — their answer, never written by a pin |

A sub-area is additionally cleared whenever the town moves underneath it, even a
user-chosen one: a block belongs to exactly one town, so a DHA phase is meaningless once
the town is Clifton.

**Street stays blanks-only**, deliberately. It is the one field carrying something a person
may have typed at length, and the hint behind it is a raw geocoder string rather than a
registry value, so it has not earned the right to replace their words.

Applied to `ConfirmAddressModal`'s "Adjust pin" too (owner request). The mount effect
prefills from the SAVED coordinate; `prefillFromAdjustedPin` asks the same question again
about one the user has just moved. Without it the modal keeps describing the old pin, which
is the more misleading of the two hosts — its entire claim is "here is where we think you
are, confirm it".

`suggestedAreaRef` moves with it, and only when the prefill actually applied — which is why
`applyPinPrefill` now returns a boolean. That ref is what `area_overridden` measures prefill
accuracy against; left pointing at a suggestion made for a superseded pin, it would report
overrides nobody performed.

### A town change no longer clears the pin (owner ruling, 2026-08-26)

Reverses the P1-4 sibling from `7db6ea7`. Found by a test that would not pass and turned out
to be describing a real trap:

1. Pin placed -> town auto-fills "DHA".
2. User disagrees and picks "Korangi" -> `selectTown` cleared the pin.
3. Save blocked on a missing pin, so they re-open the map and re-place it.
4. The new pin re-derived "DHA" over their correction. Back to step 1.

**No sequence of actions saved a town the geocoder disagreed with**, and `area_overridden` —
the event built to measure exactly that disagreement, and which QA 40 calls its first-ever
live event — could never fire.

The rule was not wrong, it was out of date: it was written when the town was chosen BEFORE
the pin, where a stale pin could be ~30km out. Under Province -> City -> Pin the dependency
is inverted — the pin is placed first and PRODUCES the town — so a town edit says the
geocoder read the coordinate wrongly, not that the coordinate is wrong.

`CLEARED_PIN` moved from `CLEARED_BY_TOWN_CHANGE` to `CLEARED_BY_CITY_CHANGE`. **A CITY
change still clears the pin**, untouched: a different city makes the coordinate provably
wrong, which a different town within one city does not. That asymmetry is the ruling, and
the clearing-set tests assert it directly.

`__tests__/confirmModalAdjustPin.test.tsx` now proves the override path works end to end —
correct the town, save, and `area_overridden` fires against the suggestion THIS pin made.

**QA 33 in `p2-capture-flow.md` asserted the old rule and now asserts the opposite.**

**One residual case, stated not fixed:** a legacy user who moved house within the same city
can now change their town while keeping a pin that describes where they used to live.
Previously the clear forced a re-pin. The pin is still required and still theirs to edit, and
the alternative was the loop above — but it is the one thing this ruling gives up.

### The confirm modal shows the province picker too (owner request)

`showProvince={false}` is gone from `ConfirmAddressModal`. The reasoning for suppressing it
— "the sheet arrives with the city already resolved from the pin" — had it backwards: a
resolved city can be the WRONG city, and correcting that in a 58-entry list is the harder
half of the job without the filter. The prop stays for a future host that wants the leaner
form.

### The same inversion, one rung up (Issue 6)

**A province change in the confirm modal destroys a correct pin.** Province clears the city
(it may not exist in the new province), and a city change clears the pin — so using the
province filter to fix a wrong city throws away a pin that was right.

This is not hypothetical: the screenshot that prompted the request showed a pin at
`32.575, 74.070` (Punjab) under a city of "Peshawar". Fixing that city via province is
exactly the move that loses the good coordinate.

It is the SAME inversion just ruled on for town, one rung up. In the confirm modal the city
is itself pin-derived — `buildPrefill` takes it from the geocoder — so correcting it says
"the geocoder read the coordinate wrongly", not "the coordinate is wrong".

It does NOT generalise to Edit Profile, and that is why this is a question rather than a
change: there the user picks the city BEFORE placing the pin, so a city change really does
invalidate a pin placed under the old one. Same rule, opposite correct answer, depending on
which produced which.

**RULED 2026-08-26 (owner): leave it. This is intended behaviour.** The option not taken was
to stop the CITY change clearing the pin in this modal only, keeping Edit Profile as-is, by
splitting the `CLEARED_BY_CITY_CHANGE` set the two hosts share.

The argument above is real but does not carry the province rung. A town is produced by the
pin and nothing else, so a town edit can only ever mean "the geocoder read this wrongly". A
province is not produced by anything — the user chooses it, upstream of the city, to narrow a
list of 58 — so changing it says the whole place is wrong. Carrying a coordinate across that
would let the Punjab pin above sit under a Peshawar address and pass validation, which is the
precise pairing the mandatory cascade was added to prevent. Cheap and loud (one tap on
"Adjust pin") beats invisible and wrong.

No code changed. `CLEARED_BY_PROVINCE_CHANGE`'s doc comment now carries this reasoning and
says explicitly not to "fix" it, because the next reader will see the town ruling directly
above it and reach for the same conclusion.

### The map narrows Province -> City -> Area, and province is now mandatory

Two owner requests that reinforce each other: making province mandatory guarantees the
cascade is entered from the top, which is what makes a province viewport reachable before
any city is named.

`resolveSelectionViewport` gained a third rung, so the fallback chain is now
**area -> city -> province -> PAKISTAN_CENTER**, and `viewportSource` gained
`province_centroid` alongside the two added earlier.

**The province extent is DERIVED, not geocoded, and that is the interesting decision.** It
is the bounding box of the city centroids the sweep confirmed for that province —
`PROVINCE_EXTENTS`, computed at module load. A geocoded "province centroid" would be the
middle of a polygon, which for Balochistan is a point in empty desert hundreds of km from
anywhere anyone lives. What someone about to pick their city needs to see is WHERE THE
CITIES ARE. It also costs no new API calls and cannot drift from the city data, because it
IS the city data. Unlike the two rungs above it, its zoom comes from the data rather than a
fixed delta; a one-city province (ICT) gets a 0.5-degree floor so its viewport is not a point.

Coverage is total — every province has at least one confirmed city — so this also upgrades
the four cities the sweep rejected (Ghanche, Ghizer, Hub, Kotli) from a country-wide view to
their own province.

**Province mandatory** adds a `validateLocationValues` rule and marks the field required; the
city picker is disabled until one is chosen. It is still **never persisted** —
`buildLocationPayload` derives the saved province from the city, so the P2.1 defect it was
removed for (storing Karachi/Punjab) stays impossible. A test asserts that directly.

Two consequences worth knowing:

- **The pin opens from the province rung**, not just the city one. Someone unsure of their
  city can now find it on a map. Which required the next point.
- **The first choice of a city no longer clears the pin.** Clearing is for a CHANGE of city —
  a pin placed at the province stage has no old city to be wrong about, and wiping it would
  punish the exact order the province viewport exists to support. A genuine city CHANGE still
  clears it, unchanged.

**Legacy risk, stated not fixed:** a user whose saved city is not in the registry derives no
province, so the field is empty and the save is now blocked until they pick one — which
clears their city and makes them re-pick it. Previously an off-registry city saved fine (the
P0.2d path explicitly did not block on a derived-province miss). The migration path is
reasonable, but it is a behaviour change for legacy rows and it arrives with the same release
as the house-number gate.

### Save closes the modal only on a complete profile — verified, not changed

Asked for as a requirement; it turned out to be how the flow already worked, so this pass
added the tests that hold it rather than any behaviour.

Two independent halves, and neither lives in the Save button:

- **Incomplete never saves.** `validateLocationValues` runs first and returns early, so
  `onConfirm` is not called at all and the field errors render. Now covered directly,
  including that the missing field is NAMED rather than the tap doing nothing visible.
- **Closing is the host's, not the modal's.** The gate has no "close": it stops rendering
  once `user.locationVersion` reaches the completion version. The only thing that carries it
  there without a refetch is `setLocationEvaluation`, fed by the PATCH's `evaluation`
  (`currentVersion`). Three tests now cover that joint — completing, not completing, and the
  legacy save failing so nothing is stamped at all.

**CLOSED — the client reads `evaluation.missing` now.** `utils/locationEvaluation.ts` maps
the server's wire identifiers onto the words the form uses (`areaId` -> "Town", `cityId` ->
"City", `houseNo` -> the registry's own label for that area, `pin` -> "Map pin") and builds
one sentence. The gate alerts "Almost there — Your address still needs Map pin before you
can book a pickup."; Edit Profile appends it to the success alert rather than raising a
second one, because the save did succeed.

Three rules in that module worth keeping:

- **An unrecognised field is dropped, never shown raw.** A server that adds a fifth
  requirement before this build supports it must not produce "you are missing
  deliveryWindowId".
- **If nothing is recognisable, it says nothing.** "Something is wrong, we can't say what"
  cannot be acted on and undermines a save that worked.
- **The house-number label is registry-driven**, same as the form: a household is asked for
  a house or flat number, an industrial plot for a unit or building name.

The reachable case this exists for: a coordinate written by an older build carries
`location.source: "legacy_string"`, which satisfies every check this app makes and fails the
server's `pin`.

### Two defects the new message immediately exposed

Surfacing `evaluation.missing` paid for itself within minutes: a user placed a pin, saved,
and was told "your address still needs Map pin". Both causes were pre-existing and silent.

**1. The gate threw the placement away.** `handleConfirmSave` hardcoded
`buildLocationPatchPayload(payload, "derived")`, and `derived` maps to
`source: "legacy_string"` — which the server does not accept as a pin at all (only
`map_pin` and `collector_verified` count). Its comment said "a pin the user re-placed inside
the modal was already tagged by its confirm", and that tag lived in the modal's
`placementRef` and was never passed to the host. So **re-placing the pin could never satisfy
the server**, in either direction: the save succeeded, the profile stayed incomplete, and
before the evaluation was read, nothing said so. The placement now travels with the payload.

**2. The modal re-described a pin nobody touched.** Its `form.reset` passed `"derived"` for
the REHYDRATED coordinate, which meant every save from this sheet re-sent the user's
existing pin as `legacy_string`/`unknown`. For a tier A/B user — where the server does not
require a pin, so the sheet can open just to collect a house number — that **downgrades a
`building`-precision pin they deliberately placed**. That is the P0-1 defect, restated
almost verbatim in `buildLocationPatchPayload`'s own comment about an absent key meaning
"don't touch". It now passes `null`, so `location` is omitted unless this session produced
a pin.

**And the copy was wrong for the case it fired in.** "Your address still needs Map pin" in
front of a visible coordinate reads as a broken app. `missingSentence` now takes
`hasCoordinate` and, when the pin is rejected while one is on screen, says what to DO:
"Please confirm your location on the map — tap “Adjust pin”, then Confirm. Your saved pin
was placed by an older version of the app, so it needs re-confirming." Other outstanding
fields are still listed after it.

### Where client and server disagree about "complete"

Written down because it is not a bug to be fixed — the two answer different questions — and
because everything above depends on knowing which is authoritative.

**Server** (`lib/evaluateLocation.ts`), the authority. The required SET varies by coverage:

| City | Required |
|---|---|
| Tier A/B with a towns list (Karachi, Lahore, Islamabad) | `cityId`, `areaId`, `houseNo` — **no pin** |
| Tier C, no towns list, or no city | `cityId`, `houseNo`, `pin` — **no area** |

`pin` counts only when `location.coordinates` is two finite numbers AND `location.source` is
`map_pin` or `collector_verified` — never a centroid, never `legacy_string`.

**Client**, three separate definitions that do not fully agree with each other either:

- `utils/locationGate.ts` `missingFields` — userName, phone, city, town, subArea (when
  required), houseNo, pin. Its `hasPin` reads the FLAT `latitude`/`longitude` strings and
  never looks at `source`.
- `utils/locationSave.ts` `validateLocationValues` — province, city, town, subArea, houseNo,
  parseable pin.
- `utils/profile.ts` `isProfileComplete` — phone, province, city, town, houseNo, lat/lng
  merely truthy (deliberately not parseable, so no existing user's deals gate flipped).

It cuts both ways:

- **Server stricter:** legacy string coordinates pass every client check and fail `pin`.
- **Client stricter:** for Karachi the server never asks for a pin at all — `areaId` covers
  it — so a Karachi user with a town and house number is complete server-side, gets
  `locationVersion: 1`, and the gate goes quiet even though `missingFields` still says `pin`.
- **Client-only fields:** userName, phone, subArea, province. The server evaluates none —
  `areaId` is satisfied by a bare town, so a sub-area is never required server-side.
- **The one clean agreement:** `houseNo`, from `structuredAddress.houseNo` on both sides.

`LOCATION_COMPLETION_VERSION` is 1 on both, and must stay in step.

Note `evaluateLocation.ts`'s header still says "the client contains no completion logic of
its own". That stopped being true when the gate shipped.

### The two resolvers have genuinely diverged

The app resolves block names; the backend cannot, because sub-area lists are not in
`lib/data/locationRegistry.json`. The durable fix is exporting them into the shared artifact
so the backend resolves them too AND caches the result — a change to
`scripts/export_location_registry.ts` plus both committed copies. Left undone deliberately;
until then the app compensates client-side and the divergence is load-bearing, not accidental.

## THE ONE THING TO UNDERSTAND FIRST

**Ship day touches ~100% of existing users.** Completeness now includes a house number, and
no existing user has one, so essentially every user meets a blocking modal on first launch
after this ships. That was an explicit owner decision, not an accident.

The mitigation is a **server-side kill switch that must be verified before release**:

```
LOCATION_GATE_MODE=off     # gate disappears, no client release needed
LOCATION_GATE_MODE=soft    # 3 dismissals (LOCATION_GATE_MAX_DISMISSALS) then blocks
LOCATION_GATE_MODE=hard    # blocks immediately, no skip
```

The deployed server default is currently `soft`. **Confirm the client actually honours it
on a real device before shipping** — QA step 41 below. If that doesn't work, this branch
must not ship.

## Architecture, in one pass

`<LocationGate />` sits beside `<UpdateGate />` in `app/_layout.tsx`, renders null unless it
decides otherwise, and only on Home. All policy is in a pure function:

```
resolveLocationGate({ user, config, dismissals, platform, build })
  1. no user                        -> none
  2. config === null                -> none   FAIL OPEN
  3. effective mode "off"           -> none   (build below minClientBuild escalates to soft)
  4. activatedCitiesOnly && placeable && not tier A -> none
  5. locationVersion >= 1           -> none   (already confirmed)
  6. has parseable coordinates      -> confirm modal
  7. otherwise                      -> finish modal, with the missing list
```

**The pin is the discriminator, not overall completeness.** Someone with a pin but no house
number gets the confirm modal and fills it inline, rather than being sent round the form.

New modules: `utils/locationGate.ts` (57 tests), `utils/locationGateConfig.ts` (66),
`utils/locationPrefill.ts` (33), `utils/locationSave.ts`, `hooks/useLocationForm.ts`,
`components/location/{LocationFields,FinishProfileModal,ConfirmAddressModal}.tsx`,
`components/LocationGate.tsx`.

## Decisions that will look wrong without their reason

- **No points anywhere.** The mockups sell "+100 POINTS" and "Save & earn 50". `points`
  exists on the user model defaulting to 0 and **nothing in either repo awards it**. Copy
  is "Continue" and "Save". Put the badges back when an award exists — not before.
- **Nothing is locked; there is no FROM PIN chip.** The mockup shows both. They contradict
  the standing project constraint *and* the owner's own "all fields editable".
- **Province is derived, and is now SHOWN — but only as a filter.** It narrows the
  58-entry city picker and is never persisted; `buildLocationPayload` still derives the
  saved `province` from the chosen city. That distinction is the whole reason the original
  field was removed: an independently-chosen province lets someone save Karachi/Punjab,
  which the registry says cannot exist. Nothing about persistence changed when the picker
  came back (owner request, this pass).
- **Street address is optional now**; house number replaced it in the completeness rule. A
  house number routes, a free-text street does not.
- **A city change clears the house number; a town change does not.** P2-15, above.
- **The centroid tables are partial on purpose**, and every consumer must keep handling a
  miss. P2-6, above.
- **Dismissals are session-scoped** and re-arm per Home visit. The durable never-ask-again
  signal is the server-stamped `locationVersion`, which survives reinstalls.
- **The gate fails open everywhere.** No config, malformed config, missing `locationGate`
  key — all resolve to "no modal". A broken config must never lock the userbase out.

## Later pass — Karachi prefill widened beyond DHA and Korangi (`c4805ed`)

**The prefill was never weak in other Karachi areas. It was switched off in them.**
`shouldPrefillArea` gated on `AREA_META[...].geocodePrefill`, and exactly two entries in the
whole registry carried `true`: `Karachi::DHA` and `Karachi::Korangi`. Everything else was
`false` under P0.6's evidence gate (precision >=85% at n>=20). On the 466 cached sweep points
that meant a town was pre-selected for **36% of pins**, and the modal looked broken
everywhere outside those two areas.

Two things changed, and they are independent — read them separately.

### 1. The resolver was losing 42% of candidates to four fixable shapes

P0.6 measured precision over *prefill-eligible* answers and never asked why 197 of 466 points
resolved to nothing. Four systematic shapes, none needing new sampling:

| shape | example | points |
| --- | --- | ---: |
| town ALIAS never stripped off a block string | `Gulistan e Johar Block 16` | 27 |
| trailing unit real but unlisted for that town | `Shah Faisal Block 5` | 42 |
| bare unit token vs. the registry's block label | `Nazimabad 4` | 15 |
| parenthetical sub-area, one half returned | `Ancholi` for `Block 20 (Ancholi)` | — |

**The first is the one to understand.** `Gulistan-e-Jauhar` already carried the alias
`Gulistan e Johar`, but `extractSubAreaForTown` only ever stripped the CANONICAL town name —
so every `Gulistan e Johar Block N` string fell through the resolver and landed on the
administrative parent `Gulshan-e-Iqbal Town` instead. Not "failed to resolve": **filed under
the wrong town, at full confidence, 27 times.** It also contaminated Gulshan-e-Iqbal's own
precision, which is part of why P0.6 read it as genuinely unreliable (56%) rather than
polluted.

After the fixes: aggregate residential precision **76% -> 87%**, town prefill **36% -> 62%**,
zero new API calls. **PECHS (n=20, 100%) and Gulistan-e-Jauhar (n=21, 90%) now clear the
original gate on their own** and join DHA and Korangi as `measured`. Both were blocked by
sample size, never by accuracy.

Two regressions were introduced and removed *during* the work. Both are easy to re-introduce
and are locked by tests:

- Accepting any unit-shaped remainder resolved `DHA Phase 99` to DHA. Where the registry
  enumerates a unit type it is authoritative about which ones exist.
- Inferring a PARENT from a suffix-stripped sub-area name sent bare `Shah Rasool` to Clifton
  (which lists `Shah Rasool Colony`), dragging 12 DHA-labelled pins with it and costing
  Clifton 39 points of precision. That strip is now confined to choosing a sub-area *under a
  town already agreed*.

### 2. The prefill policy changed — owner decision, not evidence

Karachi is now opened to **flagged provisional prefill**: an unmeasured residential Karachi
area IS pre-selected, and carries a visible amber "we guessed this from your pin" note. The
reasoning the owner accepted: the modal is a confirmation surface, so a wrong guess costs one
tap while a blank costs one tap from everyone.

**The cost this accepts, stated plainly: a user who taps through without reading keeps a
wrong area.** Two things bound it — the guess is labelled rather than presented as an answer,
and `area_overridden` measures how often it is wrong. That telemetry is what should
eventually move each area onto `measured` or onto `PREFILL_DENYLIST` (the 70%/n>=10 floor,
empty today). The 85%/n>=20 gate is untouched and still governs `measured`; it is simply no
longer the only tier.

`scripts/measure-karachi-prefill.ts` recomputes the whole per-area table offline from the

### What a reviewer should look at hardest

`buildPrefill` gained a `townSource` field. The modal used to infer provenance by comparing
the town to `geo.areaName`, which answers "user-chose-this" for every SECOND-PASS resolution

would have been invisible on exactly the pins this change affects. `area_overridden`
deliberately stays on the old narrow condition so an existing metric is not silently
redefined mid-flight.

### DEFECT FOUND — a cache hit halves the prefill

`app/api/location/reverse-geocode/route.ts` returns **`unmatched: []` on a cache hit**, by
design: re-deriving would re-log every still-unmatched candidate through `console.warn` on
every repeat hit for a popular cell. That was cheap when the client's second pass was a
nicety. It is not cheap now — that pass produces **47% of all prefills**.

Measured on the sample, the same coordinate seen twice:

| | town pre-filled | sub-area | precision |
| --- | ---: | ---: | ---: |
| fresh (`unmatched` populated) | 62% | 36% | 87% |
| **cache hit (`unmatched: []`)** | **33%** | **9%** | **76%** |

So the FIRST user at a coordinate cell gets the good prefill and everyone after them gets
roughly half of it, silently. `blockHint` survives the cache, so sub-area recovery for a
server-resolved town still works — it is the town-level second pass that goes dark.

**Not fixed here — it is a backend change and nobody has ruled on it.** The two options are
persisting `unmatched` on the cache document (a schema change; correct and durable) or
re-deriving it on read without the `console.warn` (no schema change; loses the
alias-backlog's dedupe reasoning). QA 72 records what a tester will actually see.
